# 3D 整体跟随与打乱首步卡顿检查

检查日期：2026-10-16。按用户补充，第一项指魔方未打乱、只整体转动时的姿态跟随顿挫。此次为诊断，未修改应用源码、构建文件或个人成绩。

## 已确认：慢速姿态被两次抑制

输入过滤位于 `public/gyro-orientation.js:1–12,56–77`：

- 小角度阈值为 0.007 弧度，约 0.40°。
- 小幅变化在约 66.7 毫秒后才被强制接收；模拟 100 Hz 输入、每秒 1–5° 匀速转动时，实际接收间隔为 70 毫秒，约 14.29 Hz。
- 动作分类比较的是速度差值，不是速度大小。匀速转动时速度差值接近零，也容易被归入低频路径。

绘制端位于 `public/app.js:68–70,8777–8827`：姿态变化判断阈值约 0.069°，继续动画的剩余角度阈值约 0.138°。慢动作的逐帧小变化会再次被忽略，动画循环也可能过早结束。

浏览器内存对照（相同模型、每秒 3° 匀速姿态，约 100 Hz 发送；不持久化测试参数）：

| 测试条件 | 模型绘制次数/秒 | 一秒屏幕帧中姿态发生变化的帧数 | 最大单次姿态跳变 |
| --- | ---: | ---: | ---: |
| 当前逻辑 | 14.05 | 14 / 61 | 0.230° |
| 仅放宽输入过滤 | 29.03 | 30 / 60 | 0.111° |
| 同时放宽输入和显示端阈值 | 59.80 | 60 / 60 | 0.062° |

对照仍使用原模型：2 次绘制调用、120 个三角形、无纹理。正常绘制回调大多为零点几毫秒。屏幕回调通常仍以约 60 Hz 运行，因此主因是有效姿态变化被抑制，而不是模型几何计算量太大。

## 已确认：更换新打乱后的首步被下一把手势暂存

用户补充保持连接、更换新打乱也经常出现后，沿真实动作公共入口补测，确认存在明确的主动等待。

`public/app.js:11202–11399`：`handleBluetoothMovesForCurrentState` 在打乱校验前先处理下一把手势。处于 ready、当前同步状态为复原状态时，任何单个顺时针或逆时针面转都会建立 `deferred: true` 候选，暂不传递给 `applyScrambleGuideMoves`。手势窗口为 700 毫秒，定时器实际设置为 700 + 40 毫秒。下一步若不是反向回转，先补交第一步；若是反向回转，则识别为切换下一把。

模型已经预热、持续连接的浏览器复测：

| 动作 | 立即进度 | 首步交付时间 |
| --- | ---: | ---: |
| 新公式首步 R，之后不转 | 0 | 754 毫秒 |
| 再换公式，首步 L，之后不转 | 0 | 751.6 毫秒 |
| 首步 F，约 100 毫秒后继续 U | 0 | 约 103 毫秒，随后进度直接为 2 |
| 一次传入 R2 token | 1 | 同步处理约 0.6 毫秒 |

R2 仅说明单个半转 token 不匹配手势规则；真实设备可能把半转上报为两个单转，不能据此推断设备上的所有 R2 都不受影响。

GAN 解码路径在 `public/app.js:6323` 也调用上述公共入口，因此此等待不是文本模拟特有行为。`updateBluetoothPhysicalState` 在存在 deferred 候选时还会跳过打乱进度同步，后续状态包不会自然消除该等待。具体 3D 画面可能仍由独立状态包更新，不能将进度延迟一概等同于所有协议的模型层转动延迟。

此前热启动测试直接调用 `applyScrambleGuideMovesForTest`，绕过了手势入口。因此其低耗时结果只能证明下游正确动作处理轻量，不能排除实际首步入口延迟。当前补测使用原始应用源码，临时在浏览器内暴露公共入口，没有修改生产源码；未接真实硬件。

## 首步的附加因素：冷启动阻塞与视觉过渡

初始化位于 `public/app.js:8307–8485`。Three.js、WebGL 上下文和模型在启用预览时延迟建立，没有在可交互前调用 `renderer.compileAsync` 等待图形资源准备完成。首个绘制承担首次程序使用、材质及缓冲区准备。

第一轮当前构建实测：首次 3D 绘制回调约 350.2 毫秒，出现 353 毫秒长任务；正确首步的同步处理为 0.2 毫秒。相邻后续动作的绘制通常约 0.2–0.7 毫秒。此时 72 毫秒的转层动画会在阻塞期间耗尽，随后很快到达结束状态，造成首步跳过大部分可见中间帧。

对首次绘制进一步分类：

- 图形缓存已热的新页面，首个绘制约 8.7 毫秒，上下文建立约 6.8 毫秒。
- 为排除编译缓存，在临时页面对贴纸着色器加入不可见的微小常量变化，首个绘制约 27.8 毫秒，其中 `getProgramInfoLog` 同步调用约 18.8 毫秒。
- Three.js 本地实现 `node_modules/three/src/renderers/webgl/WebGLProgram.js` 的首次使用路径会同步查询程序、着色器状态及日志。

最初 350 毫秒样本未记录全部 WebGL 调用，不能把整段时间全部归给某一个编译函数。已确认的是：首次绘制存在明显冷启动阻塞，且同步程序查询是可观测的阻塞来源。

保持连接、模型预热后，连续更换新公式并执行正确第一步，每种条件测 8 轮：

| 条件 | 首步同步处理最大值 | 下一次模型绘制回调延迟最大值 |
| --- | ---: | ---: |
| 普通桌面浏览器 | 1.0 毫秒 | 15.3 毫秒 |
| 浏览器 CPU 降速 4 倍 | 0.7 毫秒 | 7.3 毫秒 |

两组都正确到达进度 1。第二组在更充分热身后执行，不能据此认为降速后更快；这些数据只表明绕过手势入口后，下游正确首步处理未出现数百毫秒计算阻塞。帧相位也会影响“下一帧”等待时间。

公式进度反馈另有明确的视觉延迟：`public/styles.css:3016–3030` 为颜色设置 240 毫秒过渡，为透明度、阴影、位移设置 280 毫秒过渡。状态已经更新后，外观仍会逐步变化。此项是响应观感因素，不能当作已经证明的计算卡顿原因。

## 修改建议

1. 优先解除手势识别对正确首步反馈的阻塞：正确的公式动作立即推进进度及动画，同时独立保留手势候选；若后续反向回转命中原有下一把手势，清理候选并通过现有下一把流程重置。候选不能再阻断正常进度及物理状态同步。保留原手势语义，并覆盖单转、半转分包、反向回转、超时、换公式时清理候选等情况。错误首步的纠错提示和计算可单独短暂延后，避免手势首段误触发错误反馈。
2. 将静止检测与动作采样分开，保留慢速转动的新姿态，按显示帧合并消费最新样本。
3. 根据运动状态调整显示端的小角度停止条件，避免小幅运动被再次丢弃；静止时继续停止无效绘制。测试放宽参数仅用于证明根因，正式实现需要一并验证静止防抖。
4. 在预览就绪前完成图形程序预编译及首帧资源准备，首次转动不承担冷启动工作；转层的视觉时间线应考虑首个可见帧，避免初始化期间动画已经结束。
5. 缩短转动进度反馈的颜色、位移过渡；提前建立公式节点，避免首次状态同步临时切换文字结构。
6. 后续用真实 GAN 验证各协议的首步进度与画面呈现时序。当前已确认公共入口约 740 毫秒的主动等待；冷启动为另一个独立问题。
