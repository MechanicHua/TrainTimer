# TrainTimer 多平台 App 迁移方案

本方案将现有 TrainTimer 转换为以 Flutter 为主体的离线应用，优先交付 macOS 和 Windows，后续扩展 Android 和 iOS。首要目标是代码职责清楚、界面容易调整、运行高效、动画及时跟手，同时保留计时、蓝牙魔方、分析和复盘的主要能力。

需求依据截至 2026 年 10 月 18 日的逐项讨论。技术路线、功能范围和性能目标已确认；3D 后端、原生玻璃组合方式及平台兼容性由第一阶段原型决定。已有求解器研究数据属于候选算法基准，不能视为新版 App 的运行成绩。

开发、构建和测试输出限定在新版目录及其产物目录。旧版仅作为只读行为对照，不再运行会改写旧版运行包的同步脚本。

## 四 计时与生命周期

计时流程使用明确的状态转换：准备打乱、等待起表或观察、键盘蓄备、计时、成绩保存和完成。蓝牙连接状态独立管理，断线不会直接把计时器重置。关闭观察后仍保留“打乱到位后等待下一次转层”的状态。

| 情况 | 确定行为 |
| --- | --- |
| 键盘起表 | 默认空格，可改键；按住 0.5 秒后松开起表；过早松开取消蓄备 |
| 键盘停表 | 任意普通按键停表；文本输入、快捷键录入和必要系统组合键不误触发 |
| Esc | 计时中结束并记为 DNF；观察中的取消沿用清晰的独立语义 |
| 蓝牙准备 | 达到目标打乱后自动准备；观察开启则立即开始观察，否则等待下一次转层 |
| 蓝牙起表 | 目标状态之后的新转层起表；打乱最后一步、重复包、补发历史不误触发 |
| 蓝牙自动停表 | 根据可信动作和复原状态结束；异常时保留手动结束入口 |
| 整体姿态变化 | 只改变展示，不视为转层，不触发起表 |
| 观察处罚 | 小于 15 秒正常；15 秒起 +2；17 秒起 DNF；罚时状态与实际复原用时分开保存 |
| 下一把手势 | 复原状态下短时间正转再反转，默认开启；动作先即时显示，识别过程不延迟正常反馈 |

观察处罚以起表时的实际耗时判定，显示四舍五入不影响边界。8 秒和 12 秒提醒沿用现有能力。达到超时状态后仍能显示清晰的处罚结果和结束入口。[WCA A4d](https://www.worldcubeassociation.org/regulations/#A4d)

取消旧版打乱完成后固定 1 秒的起表屏蔽。按有序、去重后的动作逐个处理，准确识别到达目标的那一步；同一个数据包内的后续新动作也必须能够起表并进入动作记录。

计时以单调时钟推进，显示刷新频率不决定成绩。蓝牙动作同时保留设备时间、主机接收时间及其可靠性；设备时间的回绕、校准和补发在协议层处理。GAN i4 原型要验证设备区间时间与主机计时的关系，再确定最终采用方式；无可靠设备时间时使用主机单调时间并记录来源。低帧率或布局动画不能改变起停时间。

| 生命周期事件 | 确定行为 |
| --- | --- |
| 进入蓝牙模式 | 尝试连接上次使用的设备；第一次由用户选择 |
| 主动断开 | 取消自动连接意图，不立刻自动连回 |
| 意外断线 | 后台按逐渐延长的间隔有限重试，可取消；达到上限后提示手动重连 |
| 计时中断线或缺步 | 计时继续，可手动结束；标记数据不完整，限制依赖缺失证据的分析 |
| 重新连上 | 获取当前状态，按设备能力补动作、去重并校准；完整状态包不等于完整历史 |
| 最小化或完全不可见 | 电脑唤醒时保持连接和自动计时，暂停不可见绘制，回来直接显示最新状态 |
| 仅失去焦点但仍可见 | 按可见性继续必要显示；不因为失焦就停止全部绘制 |
| 观察或计时期间 | 暂时阻止闲置引起的息屏与睡眠，结束后释放 |
| 实际系统睡眠 | 当前这把标为中断并保存；醒来后由用户选择记为 DNF 或丢弃，待处理期间不混入有效成绩统计 |
| 关闭窗口 | Windows 和 macOS 均退出；观察或计时中先确认；后台使用最小化 |

重试间隔和次数作为集中配置，通过 GAN i4 原型确定合理默认值。数据恢复、连接重试和绘制使用不同状态，避免“蓝牙重连完成”意外覆盖正在进行的计时。

## 五 蓝牙设备接口

传输层负责扫描、连接、发现特征、订阅、读写和系统权限。协议层负责握手、加解密、消息解析、动作序号、设备时间和状态解码。两者之间传递数据，不把 GAN 指令写进界面控制器。

统一事件至少覆盖连接变化、转层、完整状态、姿态、电量和诊断信息。每个事件包含来源、顺序标识、时间信息及必要的数据质量说明。设备能力分别声明是否支持完整状态、历史补发、姿态和电量；缺少某项能力的品牌仍能接入其可用功能。

首个协议适配器围绕 GAN i4 验收。现有 GAN Gen4 解析路径中，转动、完整状态、姿态和历史信息是不同消息，迁移必须保留这种区分。当前状态校准可以修正显示，却不能凭空生成中间动作和用时。

原型重点验证 macOS 的设备身份与协议解密所需信息能否稳定取得，以及 Windows 的订阅、断线恢复和蓝牙适配器差异。若需要用户补充设备信息，先呈现具体限制和可用流程，不把未经验证的自动识别写成已支持。

原始通信诊断采用有限、可关闭的日志缓冲。复盘证据按每把持久化，不能把无限增长的调试日志作为长期成绩格式。

## 六 本地打乱与通用状态求解

### 打乱生成

全部现有项目使用本地实现，对照选定版本 TNoodle 的规则与实现逻辑逐项移植。三阶优先打通，其余项目在完整功能阶段交付。计算表、算法初始化和预览按需加载，空闲时预取少量下一条打乱。

打乱生成器负责合法目标状态与生成规则；通用求解器负责把当前状态转为目标状态。两者共用魔方状态表示和转动语义，但不把“随机转若干步”当成所有项目的统一替代算法。

验收包括状态合法性、符号和转动语义、打乱后预览一致性，以及与参考实现的固定样例和批量对照。记录算法版本、生成来源和必要的种子信息。兼容实现用于本地训练；TNoodle 官方发布与自定义实现的用途边界以其说明为准。[TNoodle 项目](https://github.com/thewca/tnoodle)

移植模块记录来源、提交和许可证，保留相应声明；测试环境可使用参考实现对照，安装包交付本地实现所需的运行代码。

### 任意三阶状态到目标状态

提供独立的求解服务，输入当前状态、目标状态和请求版本，输出公式、步数、耗时与验证结果。它不依赖打乱页面，后续需要到达指定状态时可复用。

沿用当前工程已验证的群运算约定：将当前状态 C 和目标状态 T 转成相对状态 T⁻¹C，求其到复原状态的公式；所得公式再实际作用于 C，必须得到 T。以程序状态演算确认方向，避免把公式逆序或状态乘法顺序写反。

采用已选定的原生 min2phase，输出上限为 20 HTM，R2 算一步。先检查角块、棱块、方向与奇偶性等合法性条件，非法状态进入重新同步流程。输出经独立状态演算验证后才交给界面。

| 已有实测 | 修正后的 C++ min2phase |

| 环境 | M1 Pro，8 核、16 GB，arm64，clang++ -O3 |
| 样本 | 1506 个，包括 1000 个随机合法状态对、300 个打乱纠错、200 个近目标及 6 个结构化案例 |
| 正确性 | 本轮全部验证到达目标，且公式不超过 20 HTM |
| 随机状态对 | 平均 1.79 毫秒，p99 19.11 毫秒，最慢 128.16 毫秒 |

集成固定上游提交和已有可移植性补丁，通过小型 C ABI 连接 Dart。单一求解执行者拥有可变搜索状态，避免未经验证的并发重入。计算位于后台，旧状态的结果不得覆盖当前提示；运行预算耗尽仍无合格结果时继续按后台策略处理或取消过期任务，不把超过 20 步的结果冒充达标。[候选源码](https://github.com/lilborgo/min2phaseCXX)、[可移植性补丁](/Users/huaeew/Documents/TrainTimer/output/solver-research-2026-10-18/min2phase-cxx-portability.patch)

### 自动纠错规则

1. 按当前固定引导公式推进，记住最后匹配的逻辑状态和进度。
2. 偏离后对错误片段做局部简化：同面转动按四分之一圈数合并，相邻逆动作抵消。R R 化为 R2，算一步。
3. 简化后的错误片段不超过两步，提示其逆公式；恢复到最后正确状态后继续原公式。
4. 超过两步，后台求解当前状态到最终目标状态，结果通过验证后替换为纠正公式。
5. 新公式保持整条稳定，仅推进进度；再次偏离时使用相同规则。

这项“两步”规则采用局部公式化简，不调用全局最短公式搜索来判定错误片段长度。修正求解可以覆盖任意合法三阶目标状态，但不会在用户正确跟随时每步重算整条公式。

当继续转动导致求解结果过期，保留最新待求解状态，取消或丢弃旧请求。若当前已达到目标，立即完成引导；正在计算时动作与 3D 照常响应。

## 七 3D 展示与复盘

首版仅三阶使用实时 3D 跟随与复盘，其余项目保留二维打乱预览。视觉采用清晰色块、圆角和适度明暗，围绕现有少量几何生成模型。

渲染实现先做原型比较。Flutter GPU 原生绘制是候选；可用的封装库只承担需要的能力。对固定魔方几何，也可评估基于 Flutter 绘制接口的专用投影方案，但它必须正确处理转层遮挡、透视、圆角与抗锯齿，不能凭依赖少就认定更快。最终根据两端帧耗时、延迟、清晰度、内存和维护成本选型。[Flutter 3D 说明](https://docs.flutter.dev/resources/faq)、[Canvas 三角网格接口](https://api.flutter.dev/flutter/dart-ui/Canvas/drawVertices.html)

| 对象 | 处理方式 |
| --- | --- |
| 逻辑魔方 | 接收有序动作立即更新，独立于动画进度 |
| 转层动画 | 按时间插值，快速输入时缩短过渡，必要时跳过积压中间动画，尽快追上最新状态 |
| 姿态跟随 | 使用校准后的四元数和时间，避免过大的变化阈值吞掉慢动作；平滑程度通过实机调优 |
| 动作记录 | 保存完整已接收动作与时间；动画追赶不能删除复盘证据 |
| 绘制调度 | 动作、姿态、交互和布局变化触发；静止后停绘；不可见时不绘制 |
| 相机 | 展示朝向与逻辑状态分开；手动观察角度不改变打乱判定和成绩 |
| 材质与尺寸 | 参数集中，支持深浅主题、窗口变化与高 DPI；放大后仍检查边缘清晰度 |

3D 使用独立更新区域，姿态变化不重建整个计时页面。动画依赖真实时间推进，不能把 60 或 120 次回调当作一秒。UI 动画和转层动画分别调优，避免界面弹性效果干扰魔方动作顺序。

复盘支持整把、阶段、逐步前后、进度拖动和倍速。次要控件收起；拖动后取消旧播放回调，定位到选定时刻的正确状态。较长记录按需生成检查点，从最近检查点重建目标位置，避免每次拖动从头演算。

姿态录制提供开关，默认关闭。开启后保存紧凑姿态轨迹，复盘可切换实际姿态与固定视角；没有姿态数据或局部缺失时明确显示可用范围，不合成声称真实的历史朝向。旧成绩有动作即可进行对应转层复盘，原先未保存的姿态无法补回。

## 八 界面结构与动效

主要页面为计时、历史、统计和设置。左侧窄导航可收起，会话切换与蓝牙状态放在易访问的位置。

| 页面或区域 | 内容与行为 |
| --- | --- |
| 计时页待机 | 计时与打乱居中，旁边显示最近成绩和分析摘要；蓝牙模式显示 3D，辅助区可收起 |
| 正式计时 | 自动进入窗口内专注布局，保留计时、已开启的 3D、必要提示及异常结束入口 |
| 历史页 | 按时间分页浏览、会话切换、成绩选择与管理；移除筛选及标签 |
| 成绩详情 | 宽窗口右侧展开，可放大；窄窗口进入详情页；支持上一条和下一条，并保留列表滚动位置 |
| 统计页 | 现有成绩指标、历史对比、CFOP 摘要、OLL/PLL 分类统计；按全局或当前会话组织 |
| 设置页 | 模式、观察、快捷键、主题、3D 与姿态录制、蓝牙、备份与导入导出 |

深色和浅色都支持，默认跟随系统，可手动固定，并保留强调色选择。字体、字号、数字宽度、间距、圆角、颜色与动画参数集中定义。计时数字采用稳定的数字布局，防止位数变化引起跳动。

苹果端的原生 Liquid Glass 用于侧边导航、顶部工具栏和必要的浮动操作区。计时、图表和成绩内容保持清晰背景。Windows、Android 和不支持玻璃的旧版 macOS 使用相同布局与组件语义的无玻璃样式。[Apple Liquid Glass 指引](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)

少量 Swift/AppKit 代码集中在外观与导航适配中。原型优先验证原生导航容器与 Flutter 内容区的组合；涉及浮动覆盖时检查裁剪、点击命中、焦点、窗口缩放以及与 3D 的合成。Flutter 的 macOS Platform Views 存在功能和性能边界，不能将普通 Flutter 半透明控件直接视为已经实现系统原生玻璃。[Flutter macOS Platform Views](https://docs.flutter.dev/platform-integration/macos/platform-views)

页面、侧栏和按钮使用短促连贯、略有弹性的动画；连续操作能立即打断或反向过渡。计时区、3D 区域和详情面板的尺寸变化由单一布局状态协调，减少多段动画互相覆盖。系统减少动态效果、减少透明度和键盘焦点要求在组件层统一处理。

界面打磨集中在最后阶段，但基础主题、组件和动画结构从可用计时阶段就建立，以便后续逐页调整。

## 九 百万条数据的存储与统计

采用 SQLite + Drift，数据库在后台执行，使用事务与必要索引。摘要和详情在逻辑上分开，首版优先放在同一数据库中，便于一致性保存、备份和迁移。容量目标覆盖 100 万条及以上，不设为保存上限。[Drift 原生平台支持](https://drift.simonbinder.eu/platforms/)

### 数据结构

| 数据 | 主要内容 |
| --- | --- |
| sessions | 会话标识、名称、项目、显示顺序和必要设置 |
| solves | 唯一标识、会话、项目、时间、原始用时、罚时、打乱、备注、来源、完整性与详情状态 |
| solve_details | 起始状态、物理动作、时间偏移、序号、必要校准点及详情编码版本 |
| pose_tracks | 用户开启录制时的姿态时间线，独立压缩和读取 |
| solve_analysis | CFOP 分段、步数/TPS、观察估计、OLL/PLL 事件、分析版本和原始记录修订号 |
| statistics_cache | 可重建的会话或全局聚合、曲线摘要、滚动指标和版本 |
| settings 和 devices | 应用设置、记住的设备及设备能力；安全敏感信息按平台适当保存 |
| active_attempts 和 operations | 进行中或中断记录、短批次落盘位置、迁移与必要撤销信息 |

业务时间采用统一整数单位；开始日期保存为 UTC 时间，运行中的间隔使用单调时钟。时间精度及来源随协议记录，不因使用更细的存储单位就宣称设备具有更高测量精度。

一把成绩的设备名、协议和起始时间只保存一次。动作以紧凑序列和相对时间保存，不重复写入完整元信息；原始通信包与业务动作分离。块编码包含版本，解码后保留物理动作与状态校准点，逻辑步数由明确规则推导。

记录使用跨设备稳定的唯一标识，数据结构、原始证据和分析结果分别管理版本。未来同步通过数据仓库接口接入，冲突处理和删除传播在同步阶段单独设计。

### 读写与统计算法

- 新成绩只插入自身、详情和必要的聚合变化；备注、罚时修改只更新受影响数据。
- 列表查询显式选择摘要列，采用“时间加唯一标识”的稳定游标；避免深页 OFFSET 扫描。
- 为全局时间顺序和会话内时间顺序建立索引；不建立筛选或标签功能的索引。
- 打开详情后才读取动作与姿态，采用按容量限制的缓存；切换上一把、下一把可小范围预读。
- 每次转动不刷新整张历史列表；停表先给出成绩反馈，再提交保存和异步分析。
- 基础计数、总时长和分布按变化更新；固定窗口平均值复用已有验证过的滑动统计思路。
- 补录旧成绩、删除或改罚时会使对应滚动窗口和最佳区间缓存失效。根据依赖范围局部更新，必要的全局重建在后台执行。
- 图表根据显示宽度做分桶和极值保留，避免绘制百万个点；显示抽样不参与统计数值计算。
- “全选”采用选择范围加例外项等紧凑表示，大批操作分批处理，避免一次构造百万条完整对象。
- 撤销记录保存受影响数据或操作信息，不复制整份数据库作为日常撤销状态。

数据库队列和导入批次有界。进行中的蓝牙记录短批次持久化并记录最后落盘序号，停表时提交最终记录；程序崩溃后的未完成记录按可恢复证据标记，不能当成完整成绩。

首轮性能样本至少包含 100 万和 200 万条，并同时覆盖单会话包含百万条成绩、多个会话和不同日期分布。样本分别包含仅摘要、常见动作数、高比例完整详情和开启姿态录制的场景。只测试没有详情的空壳记录不能代表实际容量目标。

以 N 表示历史成绩数、K 表示页面条数、M 表示一把的动作数，关键路径采用以下设计：

| 操作 | 计算量与数据访问目标 |
| --- | --- |
| 当前魔方转一步 | 更新固定数量块或面片，计算量不随历史 N 增长 |
| 新增成绩 | 插入当前记录及必要索引，索引维护约为 O(log N)；详情写入与本把大小有关 |
| 翻页 | 匹配索引的游标查询约为 O(log N + K)，只解码 K 条摘要 |
| 分析一把 | 状态序列一次线性生成，约 O(M)，供阶段分析与情况识别共享 |
| 浏览历史曲线 | 查询并绘制与视口规模相称的聚合点；原始精确统计单独计算 |
| 大批导入或统计重建 | 随处理记录量增长，分批后台执行；不挤进单次 UI 回调 |
| 完整备份 | 工作量随数据库大小增长，通过快照与后台调度控制对前台的影响 |

这些是结构与复杂度目标。实际耗时仍由记录大小、索引命中、磁盘和渲染共同决定，最终按真机指标验收。

### CFOP 与 OLL/PLL

保留 Cross、四组 F2L、OLL、PLL 的用时、步数、TPS、观察时间估计和历史对比。主页面显示摘要，详情展开。OP 在本项目中指 OLL/PLL 情况识别与统计。

一次解析动作和生成状态序列，供 CFOP 与 OLL/PLL 共用。分析结果以原始记录修订号和算法版本校验；备注修改不重新分析，动作或校准证据改变才使分析失效。后台结果提交时再次验证记录未删除、版本未变化。

观察时间仍以算法估计呈现。数据缺失时限制依赖缺失动作的指标，并保留可确认的结果；不把不完整动作数、推测阶段边界或仅有最终状态当作完整分析。公式训练和公式库不进入首版依赖链，但情况识别所需定义保留。

## 十 精简 导入导出与备份

### 手动精简旧成绩

只有用户主动操作才移除详情，不按保存时长自动清除。操作前展示范围、将删除的数据类型和预计释放空间，完成重大操作前备份后再执行。

保留基本成绩、打乱、备注、步数/TPS、已有 CFOP 分段及 OLL/PLL 识别统计。移除逐步动作、姿态和仅供详情恢复使用的冗余证据，记录“仅摘要”状态。

精简后的摘要保留当时的分析版本，仍可参加已有统计；完整回放和依赖原始动作的重新分析不可用。恢复这些能力需要仍然存在的精简前完整备份。精简涉及数据库空闲页，磁盘体积的实际回收放到可取消的维护任务中，不在计时期间强制执行。

### 迁移与格式兼容

入口统一到设置中的导入导出。仅手动选择旧文件或备份，不自动扫描旧目录。

流程为选择文件、读取结构、展示条数及字段兼容报告、暂存验证、备份现有数据、提交导入、核对结果。原文件始终保留。无效记录定位到具体条目，取消或失败不能留下被误认为完整导入的半成品。

保留 TrainTimer JSON/CSV、csTimer 导入导出及 CubeDesk 导入。导入器统一转换到内部模型，再写数据库；导出器按目标格式能力映射。新版本完整备份保存复盘详情、设置与版本清单，不能把不含这些字段的 CSV 当作完整备份。

大文件采用增量解析、分批落盘和后台执行。能稳定识别的重复记录按来源标识处理，不仅凭同时间同成绩去重。导入报告明确新建、跳过、冲突和不支持的字段；旧标签在兼容扩展字段中保留，不重新启用标签功能。

### 自动备份

| 项目 | 已确定策略 |
| --- | --- |
| 日常备份 | 有数据变更时每日一次 |
| 保留数量 | 最近 7 份日常备份，数量可修改 |
| 重大操作前 | 精简、批量破坏性操作、覆盖导入或数据结构升级等操作前另存备份 |
| 操作前版本 | 独立轮换，保留最近 3 份，数量可修改 |
| 手动导出 | 用户自行管理，不加入自动轮换删除 |
| 保存目录 | 默认应用备份目录，可在设置中更改，包括其他磁盘 |

应用运行时根据本地日期和数据修订号调度日常备份；关闭期间不额外安装后台守护程序，下一次启动补做必要的最新备份。

备份通过 SQLite 一致性快照方式生成，再封装校验清单和必要配置。不能只复制仍在写入的主数据库文件而遗漏 WAL 中的数据。生成临时文件、校验可读性与内容后，再完成替换和旧版本轮换。[SQLite Online Backup API](https://www.sqlite.org/backup.html)

重大操作前备份失败时，保留原数据并显示原因，待重试或用户重新决定后再执行该操作。轮换只清理应用管理且已识别的备份文件。恢复在临时位置校验结构和版本，通过后再切换数据源。

备份属于后台任务，限速和分块以减少对计时的影响；取消保留最近一次有效备份。完整详情较多时要报告实际备份大小和耗时，有限版本数不等于固定磁盘容量。

## 十一 分阶段实施与交付物

### 第一阶段 关键原型

在独立目录建立最小 Flutter 工程与可重复测试夹具。蓝牙、渲染、玻璃和数据原型尽早覆盖真实组合场景。

| 原型 | 必须得到的结果 |
| --- | --- |
| GAN i4 | macOS 和 Windows x64 完成连接、动作、状态、姿态、重连；首步与补包顺序正确 |
| 三阶 3D | 快速转动与慢姿态均连续，静止停绘；验证转层遮挡、高 DPI 和布局动画 |
| 原生玻璃 | 验证导航、工具栏、必要浮动区与 Flutter 内容、键盘和 3D 的组合；旧系统回退清楚 |
| min2phase | 固定版本加补丁，通过三种桌面架构构建与可运行环境的求解回归；算法结果到目标且不超过 20 HTM |
| SQLite | 完成 100 万及 200 万条混合数据的首屏、分页、会话切换、插入和统计重建测量 |
| 打包基础 | macOS ARM64、Windows x64、Windows ARM64 的依赖与构建清单；未有设备的项目标为待真机验收 |

交付小型可运行原型、测量报告、确定的渲染后端和平台限制。未达目标时先给出具体原因与优化方案；涉及调整已确认的效果、兼容范围或指标时，再由用户决定。

### 第二阶段 可实际使用的计时流程

先完成三阶的正常键盘计时与 GAN i4 蓝牙路径：打乱、自动纠错、观察、起停、3D 和成绩保存。接入连接恢复、最小化、睡眠中断、退出和本地持久化。

同步建立侧栏、主题、计时数字、基础按钮和动画参数。主界面能够日常使用，动作记录与保存可靠，计时独立于分析和列表刷新。

交付可安装的核心体验版本及问题清单，重点检查手感、首步响应、下一把手势、转错后的引导与保存正确性。

### 第三阶段 完整功能

补齐全部打乱项目、二维预览、会话与历史、CFOP/OP 分析统计、详情与复盘、导入导出、备份、手动精简及姿态录制开关。

逐项对照功能范围，保证筛选、标签、公式库和专项训练不重新进入首版。使用旧数据副本迁移验证，同时检查百万条数据与大量动作详情下的读写表现。

交付功能完整的桌面测试版本、格式兼容报告和数据恢复演练结果。

### 第四阶段 界面打磨与交付验收

逐页调整比例、留白、字体、颜色、玻璃区域、状态提示和动画中断行为。测试宽窄窗口、深浅主题、高 DPI、键盘操作、60/120 Hz、后台运行与长时间使用。

完成安装、手动升级、数据库升级前备份和恢复演练。应用包包含自身运行所需依赖，用户无需另行启动 Chrome、Node、HTTP 服务或 Java。

交付 macOS ARM64 应用包及安装载体、Windows x64 安装包和 Windows ARM64 构建。打包阶段验证签名、公证或签名状态说明、首次启动权限和蓝牙访问；附版本号、变更说明、校验信息、已验证设备及已知限制。

Windows ARM 没有真机时只能保留“构建完成、真机待验证”的交付状态，不能列入已经验收通过的平台。macOS/x64 的验收报告与 ARM 状态分别呈现。

## 十二 验收目标与测量口径

以下是用户确认的目标，尚不是新版的实测成绩。原型未达标时先分析和优化，再讨论是否调整，不能静默降低。

| 场景 | 验收目标 | 测量口径 |
| --- | --- | --- |
| 常规转动、滚动、面板动画 | 稳定 60 FPS，稳态超预算帧比例小于 1% | 分别记录 UI 与绘制耗时；60 Hz 每帧预算约 16.7 毫秒，并检查实际显示连续性 |
| 高刷新屏 | 争取稳定 120 FPS | 预算约 8.3 毫秒；单独报告高刷结果，不替代 60 FPS 基线 |
| 已解码动作到画面开始响应 | 95% 在两个屏幕刷新周期内 | 60 Hz 约 33.3 毫秒，120 Hz 约 16.7 毫秒；不要求整段动画在此时限结束 |
| 蓝牙无线链路 | 实测并单独报告 | 区分真实动作、通知到达、解码、帧提交和显示；不把软件内部耗时冒充完整链路延迟 |
| 进程冷启动 | 常用三阶计时页 2 秒内可操作 | 包含首次三阶打乱就绪和必要本地数据；首次安装初始化、导入与结构升级单列 |
| 百万条历史 | 首屏、分页和会话切换 95% 在 200 毫秒内显示结果 | 从用户动作或页面请求到摘要呈现，包含查询与 UI；成绩筛选已移除 |
| 大范围统计与数据操作 | 后台执行、有进度、可安全取消，界面保持响应 | 取消时保持已提交数据一致；提交中的短事务结束后再取消后续批次 |
| 静止与不可见 | 无应用主动维持的无效动画循环；隐藏区域停止绘制 | 蓝牙接收和必要存储继续，不把后台业务活动算作绘制 |
| 长期运行 | 有界队列和缓存，预热后无持续性内存泄漏 | 反复复盘、开关详情、长时间连接和窗口切换，记录内存曲线 |

性能定位使用真机 Profile 构建，交付体验使用 Release 构建复核；不以 Debug 或模拟器表现判断交付速度。记录版本、设备配置、刷新率、数据规模、冷暖条件、样本数、p50/p95/p99、最慢案例及原始结果。Windows x64 设备的具体 CPU、内存和图形配置在执行测量时补齐。[Flutter 性能测量](https://docs.flutter.dev/perf/ui-performance)

正常负载测试同时包含计时、3D、成绩保存和必要的后台计算。导入和备份的重负载另测，确认其调度不会持续阻塞输入。冷启动测量重复运行，明确操作系统缓存条件；不能把一次最快启动当成代表值。

### 正确性与异常验收

| 领域 | 关键案例 |
| --- | --- |
| 起停 | 0.5 秒按键边界、15/17 秒处罚边界、文本输入、重复按键、首步在同包内紧接打乱末步 |
| 手势 | 正常首步立即显示、正反手势命中、误候选恢复、不吞后续动作 |
| 蓝牙 | 断线、重复包、乱序或补发、序号回绕、状态校准、手动断开与取消重试 |
| 纠错 | R R 合并、逆向抵消、一到两步逆向、超过两步求解、求解过期和目标已经达到 |
| 模型 | 动作及其逆操作、四次四分之一转复原、任意合法状态到目标、姿态与逻辑状态互不污染 |
| 分析 | 旧版可信样例差分、跨方向、半转、状态修正、缺步限制、缓存版本与迟到结果 |
| 统计 | DNF、+2、并列、补录旧成绩、编辑和删除导致的滚动窗口变化，与简单参考算法对照 |
| 数据 | 事务失败、取消导入、磁盘不足、异常退出恢复、备份轮换、从备份恢复、精简前后摘要一致 |
| 复盘 | 拖动、倍速、逐步、阶段切换、旧回调取消、无姿态记录和缺失数据提示 |
| 生命周期 | 最小化继续计时、恢复显示最新状态、睡眠中断、退出确认、保持唤醒的释放 |
| 交付 | 干净环境安装、手动升级、旧系统无玻璃样式、ARM 依赖构建与状态标识 |

自动化测试重点覆盖计算、状态转换和数据一致性；布局和动效使用代表性画面与真机操作验收。先安排连续两小时运行与反复操作测试，再根据出现的问题增加专项测试。损坏状态、错误公式、未标记的可检测缺步和保存失败被当作成功，均属于必须修复的问题。

## 十三 第一阶段后需要落实的技术选择

这些事项属于原型的输出，不需要重新讨论已确认的功能范围：

| 事项 | 当前方向 | 通过依据 |
| --- | --- | --- |
| 3D 后端 | Flutter GPU 等原生路线候选 | 双端画面正确、流畅、低延迟，依赖与维护成本可接受 |
| 原生玻璃承载 | 少量 AppKit 导航和外观模块 | 原生效果、输入、裁剪、主题和帧率均符合目标 |
| GAN i4 原生接入 | 独立传输和协议实现 | 身份信息、握手、时间、状态及恢复真机通过 |
| 其他项目打乱 | 对照固定 TNoodle 版本本地移植 | 全项目规则、状态和预览验证 |
| 最低系统版本 | macOS 12+、Windows 10/11 的既定目标 | 所选原生依赖和实际运行共同支持 |
| Windows ARM | 原生构建目标保留 | 补充真机后才能完成无线蓝牙与性能验收 |
| 内存 功耗 包体 | 按需初始化、有界缓存、静止停绘 | 原型给出完整测量，再针对主要占用优化；目前没有已确认的绝对 MB 或功耗上限 |

实施过程中，每个阶段用可运行结果和测量报告供用户检查；遇到必须改变范围、效果或性能目标的取舍，再征求意见。旧版始终保持原状，新版依靠独立数据、验证过的导入和完整备份建立可恢复的迁移路径。
