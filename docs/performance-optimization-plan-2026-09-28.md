# TrainTimer 性能审查与优化方案

日期：2026-09-28。审查对象：当前工作区（包含已有未提交改动），不是 Git HEAD。

实施进展：见 [2026-09-29 实施与验证记录](performance-implementation-2026-09-29.md)。以下为优化前的审查记录。

本次交付为代码审查、性能基线和实施方案。没有修改产品运行代码、个人成绩文件或打包运行时。新增基准脚本与本报告；浏览器 A/B 只通过网络拦截临时改变测试页面响应。

## 1. 结论

优先修复帧调度、交互等待和主线程计算，再优化算法常数与数据结构。现有模型本身非常轻：实测 54 个实例贴片、2 次 draw call、120 个三角形、0 张纹理、DPR 1。保留 Three.js 与现有外观是合理起点。

最直接的证据：同机、同浏览器、同模拟陀螺仪输入，原版绘制约 **29.6 FPS**；仅取消渲染前的时间门限后约 **58.7 FPS**。浏览器自身 rAF 间隔两次均约 16.7 ms，静止后均无新增绘制。问题至少有一部分来自主动限帧，而非模型算不动。

打乱切换还存在确定的人为延迟：新文字延迟 680 ms 入场，再执行 640 ms 动画，总计 1320 ms。换算法库不会消除这个等待。

成熟算法已在使用：后端 min2phase 热态求解中位数约 0.63 ms；反而前端深度 8 短搜索在不命中时先占用主线程约 14 ms。停表、详情和历史比较又有重复的 CFOP/OP 分析。因此，不建议先更换 3D 引擎、引入完整 UI 框架，或把所有算法重写为 WASM。

Cube Station 可以作为体验目标；本次未测量它的帧率、内存、BLE 延迟和功耗，也没有其实现证据，不能据此认定它使用了某个引擎或算法，更不能直接承诺本项目达到同样手机表现。

## 3. 具体发现与改动方案

### P0-A：统一 3D 帧调度，解除不必要的限帧

位置：`public/app.js:51` 帧率常量；`:6926` 姿态 rAF；`:8710` 调度；`:8738` 帧门限；`:8773` 帧率选择。

当前转层目标 60 Hz，快速姿态 45 Hz、缓慢姿态 30 Hz、收敛 24 Hz。渲染函数先判断时间不足再 `setTimeout`，然后再次 rAF。60 Hz 显示器一帧 16.67 ms，45 Hz 门限是 22.22 ms；下一次屏幕刷新时仍不满足，容易隔帧才画。转层的 16.67 ms 严格比较也存在时间量化边界跳帧风险。姿态先在一个 rAF 消费，再申请渲染 rAF，还增加了一层调度等待。

实施：

1. 用一个 rAF 循环完成最新姿态消费、转层插值、实例更新和渲染；输入只写目标状态并唤醒循环。
2. 动画进行时跟随屏幕刷新，使用 rAF 时间戳计算进度，不用定时器逐帧限速。60 Hz 默认目标稳定 60 FPS；120 Hz 是否启用更高刷新由真机预算决定，不能无条件满速耗电。
3. 保留已实现的静止停止绘制、不可见暂停、姿态变化阈值和实例化。不要把所有场景改成永久循环。
4. 实时跟随、人工拖动、回放共用时钟机制，但各自保留输入语义；正常连续旋转不人为降到 24/30 Hz。

本次 A/B 只证明取消门限有效，并未实现统一调度、精确时延测量或功耗策略。正式改动需要继续验证重入、可见性变化、resize 和焦点布局迁移动画。

### P0-B：转层按时间追赶，不积压固定时长动画

位置：`public/app.js:103`，`:9143`，`:9191`，`:9207`。

每个四分之一转动画固定 72 ms，半转 96 ms。即使 CPU/GPU 无限快，单队列理论上也只能每秒处理约 13.9 个普通转层；帧对齐还会延长。20 TPS 输入实测达到队列上限 3，继续积压时会清空待播队列。它不意味着计步丢失，但会造成视觉滞后和跳变。

实施：保留全部逻辑转动和最终状态，给可视转层加入输入时间戳、序号和目标状态。依据输入间隔/队列年龄动态缩短动画，用绝对时间推进；积压超过视觉延迟预算时快速补齐中间状态，并对最新状态继续插值。区分普通实时跟随和精确回放，后者必须使用原始时间轴。不能为提高 FPS 丢弃真实 move、改计步、误触发停表，或无条件把每步都缩成 20 ms。

首次目标设为“通知处理后至首个响应帧 p95 ≤33 ms；持续 20 TPS 时视觉状态落后 p95 ≤100 ms”，之后根据设备调整。定义的是应用收到通知后的延迟，不是物理转动到显示的完整 BLE 延迟。

### P0-C：打乱切换立即响应，降低动效的绘制成本

位置：`public/app.js:9952` 克隆/样式读取；`:9989` 动画；`:10042` 预计算遗留；`public/styles.css:2951` 附近。

当前新文字 `delay:680` + `duration:640`；出场/入场实时改变 `filter:blur()`。每次切换还克隆所有后代并为每个节点读写约 25 项样式。浏览器验证了新文字的结束时间为 1320 ms。

实施：

- 新公式到达后下一帧开始呈现，旧/新交叠过渡约 160–220 ms，不等待旧公式完全消失；保留切换动效和 reduced-motion 支持。
- 首选 transform/opacity。若保留模糊外观是明确要求，评估预制模糊层交叉淡化，避免整段逐帧 blur；对长的高阶打乱和快速连点单独验收。
- 优先复用两层文字容器和稳定 CSS。必要的尺寸读取集中在写入前，避免逐节点复制整套计算样式；旧层 `aria-hidden`，最新公式始终可复制/导航。
- `scramble-blur.js` 有 Worker/WebGL 预计算，但当前普通切换链路没有调用 `scheduleScrambleTextBlurPrecompute` 或 `takeScrambleTextBlurGhost`；不能声称目前正常切换已经受 Worker 加速，也不能声称它在后台不断耗 GPU。选择接入一种经过测量的实现，或清理未使用代码与静态导入。

预取已存在，不能把“加预取”当作新方案。它目前只有一条结果、延迟 420 ms 开始补充；快连点仍会遇到约半秒的生成成本。P1 将补充有界预取队列，按 puzzle 分桶，保持锁定、切换类型和失败回退逻辑。

### P0-D：打乱修正搜索移出主线程，保留快速路由修正

位置：`public/app.js:1637`，`:11048`；`src/cube-state.js:287`，`:338`，`:867`；`src/cube-solver.js:88`、`:205`；`vendor/Min2PhaseCli.java`。

已有路由命中、错误转动回退、结果验证和缓存，值得保留。未命中后在主线程做 90 ms 上限的同步预热与 14 ms 深度 8 搜索；`requestIdleCallback` 只是推迟开始，不会让同步函数变成并行计算。预热超时的深层 Map 会被丢弃，再试可能重建。

实施顺序：

1. 把现有短搜索原样迁入专用 Worker，先维持算法结果，避免线程迁移与算法重写同时发生。路由命中和少量错误回退继续在主线程快速完成。
2. 深度 1–4 的局部错误命中很好，应保留；深度 8 并非总是值得先跑。用浅搜索、节点预算与后端热态数据比较，决定是否直接提交 min2phase；不能让无用的前置搜索拖后成熟求解器。
3. 建立 `(targetRevision, stateSequence, requestId)` 协议：只显示匹配当前目标和状态的结果，队列只保留最新尚未执行任务，旧结果最多缓存。保留“执行返回公式确实到达目标”的校验。
4. 处理真取消：当前前端等 active 请求结束后才启动最新请求；后端共享求解把 `signal` 设成 null，取消调用方主要是不再等待，不代表 JVM 搜索停下。Worker 同步搜索同样不能靠排队的 cancel 消息立即打断。用可切片搜索/短预算探测、协作取消或有节制的 Worker 重启；共享任务需保留订阅者计数，不能取消其他调用者仍需要的任务。
5. 保留已有持久 JVM、去重、缓存和 10 分钟闲置退出机制；连接训练时预热，低内存/断开时按策略释放。预热状态必须随服务代次/退出失效，避免“曾预热过”误当作“现在仍热”。后端就绪等待也应纳入完整请求超时，而不只在 READY 后启动搜索计时。

P1 再考虑用紧凑 cubie 坐标、预计算转移/剪枝表替代深度 BFS 的 54 字符状态、Map/Set、路径字符串和对象分配。只有测出收益后才做；Worker 迁移降低界面阻塞，不必然降低总 CPU 或内存。

“最近修正”目前不等于全局最短：有界短搜索超时后返回 min2phase 可行解，回退路由也可能较长。保留现有解的有效性与策略，不把更短公式或严格最优解作为未获验证的承诺。

### P0-E：停表立即显示，分析共享上下文并后台完成

位置：`public/app.js:2701`，`:4135`，`:4227`，`:14752`；`src/op-analysis.js:299`、`:334`；`src/cfop-analysis.js:73`。

`finishTiming` 在更新 `appState='saving'`、最终时间文本和让出绘制之前，同步运行 `cfopStagesForSave` 与 `opEventsForSave`；后者又调用一次 `solveCfopAnalysis`。OP 还重建快照、扫描候选、在多朝向下重复识别。60/120 步合成样本分别约 22/42 ms，足够跨过一个或多个显示帧。

详情 `cfopDisplayForSolve` 的默认参数也立即调用分析，即使已存当前版本结果。历史比较缓存随整个 `solves` 数组引用改变而失效，`cachedCfopHistoryIndex` 对有原始证据的每条成绩重新分析；这是数据量增长后的放大器。

实施：

1. 通知处理时捕获停表时刻和不可变成绩快照，立即冻结显示；先可靠保存原始数据，再提交分析 Worker。UI 显示分析待完成，不阻塞下一把训练。
2. 一个 `analyzeSolve` 返回 CFOP、OP、时间轴和统计共用结果。统一解析物理步骤/逻辑步骤/状态修正，不让 OP 再次调用完整 CFOP。按需生成对象视图，内部快照可用紧凑 facelet 缓冲。
3. 以 `solveId + rawRevision + analysisVersion` 缓存。当前版本、输入匹配且状态为 completed 的结果（包括空 OP 结果）直接使用；旧版本或原始数据变化才后台重算。WeakMap 只按对象身份命中，HTTP 每次重建对象会失效，不能承担跨请求结果缓存。
4. Worker 结果写回使用 revision 比较，防止用户编辑打乱或收到补充状态包后旧分析覆盖新数据。rawRevision 必须包含会影响阶段时间的 duration/inspection、move 时间和状态日志等，不能只比较首尾 move 或数组长度。
5. 保留停表后状态日志补捕获；新证据只使该条成绩分析失效。历史比较按时间顺序维护聚合，新增成绩增量更新，修改旧成绩更新其受影响的后缀。
6. OP 识别可按 `(facelets, orientation, kind)` 在单次分析内缓存，预计算 U 旋转/朝向的索引映射。缓存大小有界；保持 F2L 边界、多朝向 fallback、AUF、跳步、公式接受/拒绝和物理半转合并语义。

不要把“后台分析”理解为丢掉分析功能，或先写假阶段占位值。原始成绩保存与分析状态分开，失败可重试，导出必须能说明派生结果尚未完成或等待完成后导出。

### P1：复盘、历史、存储和蓝牙链路

**复盘**（`public/app.js:4870`、`:4922`）：每步从打乱重新应用 `records.slice(0, stepCount)`，顺序播完整段累计约 O(N²) 状态推进；结束回调与定时回退也可能重复应用同一步。分析时共享物理事件时间轴、保存快照/检查点，顺序播放只推进新事件，跳转用缓存索引；回放 runId 使旧 timer/callback 失效。保留真实间隔，明确逻辑半转与物理事件的映射，并将权威状态修正纳入回放一致性验证。

**历史 UI**（`public/app.js:48`、`:14535`、`:15079`）：主列表上限为 Infinity，每次行签名变化就 replaceChildren 全部行；全部成绩弹窗有 180 行分批，但分批追加不等于虚拟列表。使用可视窗口+上下缓冲行，复用按 id 管理的 DOM；排序/筛选/全选/跳到 PB 基于数据模型，不依赖已挂载行。减少跨区域 `render()`，只更新失效区域。

**滚动统计**（`src/rolling-averages.js`）：当前 buildSessionMetrics 已使用顺序最佳纪录累积，不能误判主列表每行都做 O(N²) PB 重算。剩余问题是每次全量重建窗口并排序。对于当前“去掉一个最快和一个最慢”的规则，可用滑动和、DNF 计数及单调队列维护极值，数值统计从每窗口排序降为摊还 O(1) 更新；明细展开时才排序带 id 的窗口。保留 +2、DNF、并列结果和现有裁剪语义，不顺便改变 ao50/ao100 的统计定义。

**持久化/API**（`src/history.js:42`、`:848`，`src/server.js` 成绩路由）：每次保存全文件读/parse/normalize，多次 normalize，再整库 stringify/write，并返回大量成绩。短期用单写队列、缓存规范化数据、原子替换和增量响应；处理外部文件变更及写失败。中期大历史数据用 SQLite 事务/索引、摘要分页和详情按需读取；JSON/CSV 导入导出格式不变，迁移前备份并支持回滚。Node 最低版本声明是 18，SQLite 绑定要先验证 Windows/macOS 打包，不能直接假设内置 node:sqlite 在所有安装环境可用。

**BLE**（`public/app.js:5944`、`:5993`、`:6017`、`:6187`）：已有本地同步解码、陀螺仪过滤和 8 ms 分批预算，优先保留。入队条目未带原始收到通知的时间，`packetReceivedAt` 在开始处理时获取；排队会污染延迟诊断，也可能影响基于收到时间的计时。收到通知第一时间记录单调时间、序号，沿解码/状态/停表传递；与设备时间、墙钟时间明确区分。只合并可覆盖的姿态样本，不能丢 move 或权威状态事件。初期不为小包解密强行再加一层 Worker 通信，先测 p95；同步轻量状态判定应留在最快路径。

**内存**：`previewCache` 在 `public/app.js:944` 初始化后没有容量淘汰，SVG 会随长期生成累积。增加按条数/字节约束的 LRU；同时明确 Worker、WebGL、队列、状态日志和分析快照的释放时机。用 30 分钟训练及多次连接/关闭详情检查增长，不以一次 heap 数值宣称泄漏。

### P2：模块加载与工程维护

`public/app.js` 约 652 KB、16,191 行。一次加载静态引入分析、导入导出、训练案例和约 97 KB OP 图形数据。大量职责集中增加修改回归风险，但“大文件”本身不能解释持续 30 FPS。

浏览器资源记录确认同一模块同时加载带查询参数和不带参数的地址，包括 cube-state、cfop-analysis、op-analysis、rolling-averages 等。这是不同 ESM 实例：不仅重复下载/解析，还可能分别维护缓存和初始化。建议通过统一构建/内容哈希 chunk 管理依赖，不手工给顶层 import 单独加版本号；按需加载详情、OP 图、导入导出和训练模块。利用现有 esbuild，不必引入大型框架。保持离线可用与服务白名单，并为新增 Worker 文件更新打包脚本与镜像测试。

保留目前的 WebGL 实例化方案。只有真机 GPU trace 显示材质/填充耗时超预算，才评估抗锯齿、DoubleSide、圆角 shader 和像素比的质量档位；在没有证据时不牺牲外观。CSS 背景模糊和图表动画也是 GPU/合成候选成本，但本轮未采集 GPU 时间，不能认定它们已经是主要瓶颈。

## 4. 算法库与技术选择

| 部位 | 建议 | 原因与边界 |
| --- | --- | --- |
| 3D | 保留 Three.js 0.165.0，先修调度 | 实例化已足够轻；升级版本单独测试，避免与性能重构混杂 |
| 通用 3×3 修正 | 保留现有 min2phase | 热态表现好；先解决初始化、队列和取消，不换同类库重复工作 |
| 无 Java/纯移动端未来需求 | 小范围验证 cubing.js search 或成熟求解器的 Worker/WASM 部署 | 必须比较下载量、冷启动、内存、时延及协议；experimental API 应锁版本，不承诺迁移后更快 |
| 魔方状态 | 保留已有置换表；需要时内部改 TypedArray/紧凑 cubie | 单步状态更新不是已证实的首要瓶颈；迁移必须做等价验证 |
| CFOP/OP | 优化现有领域算法和共享快照 | 通用求解器不等于“理解这次复原过程”；不能直接替代状态补偿和阶段定义 |
| TNoodle | 保留打乱引擎，验证常驻/batch 服务与有界队列 | 当前每次启动 JVM；随机步 fallback 必须继续明确标注，不能冒充同等质量打乱 |
| 持久化 | 短期增量 JSON，数据规模验证后 SQLite | 控制迁移成本，保留既有导入导出 |

参考的第一方资料：

- [Three.js：按需渲染](https://threejs.org/manual/pages/rendering-on-demand.html)：静止时不应持续画帧，动画时使用有节制的持续调度。
- [MDN：requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)：回调与显示刷新关联，应基于时间戳推进动画。
- [web.dev：高性能 CSS 动画](https://web.dev/articles/animations-guide)：优先 transform/opacity，检查 blur 等绘制成本。
- [min2phase 官方仓库](https://github.com/cs0x7f/min2phase)：Kociemba 两阶段实现、初始化和继续搜索接口；上游示例性能不作为本项目实测。
- [cubing.js 官方仓库](https://github.com/cubing/cubing.js) 与 [search API](https://js.cubing.net/cubing/api/modules/search.html)：作为候选适配层评估，而非直接替换整个显示/蓝牙系统。

## 5. 实施批次与验收

建议拆成可独立回滚的批次，每批使用同一输入重放和相同设备对照；以下目标是验收门槛，不是已经实现的指标。

| 批次 | 内容 | 完成条件 |
| --- | --- | --- |
| 0：测量 | 保留本轮基线，补 move/gyro/solve 的序号时间戳及 long-task/帧间隔分布 | 区分 BLE 收包、主线程排队、求解、首帧显示和最终状态追上 |
| 1：立即响应 | 统一 rAF、转层追赶、打乱取消 680 ms 等待 | 参考 60 Hz 设备持续输入接近 60 FPS，稳定段帧间隔 p95 ≤20 ms；静止无持续绘制；新公式下一帧开始显示 |
| 2：计算隔离 | 独立修正 Worker；独立或可调度的分析 Worker；停表先显示和保存 | 主线程关键同步片段 p95 ≤4 ms；停表显示 p95 ≤33 ms；修正不能排在批量历史分析后面 |
| 3：分析复用 | 共享分析上下文、版本缓存、历史聚合、回放检查点 | 相同原始证据与旧实现输出一致；重复打开详情复用结果；后补状态可正确重算 |
| 4：数据规模 | 历史虚拟化、增量统计/API、受控缓存、TNoodle 有界预取 | 1k/10k/50k 合成历史下输入不因全量 DOM/计算冻结；缓存命中切换与生成耗时分开统计 |
| 5：交付 | 模块构建、packaged runtime 同步、真机功耗与长时测试 | 源码启动与 macOS/Windows 安装包行为一致；性能可复现且内存增长受控 |

Worker 不需要无限开：修正与复原分析避免互相阻塞；后台历史重算可复用分析 Worker 分批运行。低核心设备控制并发，输入到来优先给交互计算。

算法验收使用已预热、缓存未命中的一组短错误与随机目标，分别报告命中率、p50/p95/p99、公式长度和端到端耗时；复杂状态允许耗时更长，但界面不能被阻塞。资源验收同时报告浏览器渲染进程、GPU 进程、Node、JVM/Worker，不能拿单个 heap 与原生 app 总内存比较。

必须覆盖的功能回归：

- 全部打乱类型、锁定/切换/连续点击、请求乱序、离线/Java 缺失、预取耗尽、错误转动和重同步。
- GAN v2/v3/v4、其他现有协议、重复包/补发/计数器回绕、陀螺仪启停、隐藏页恢复、状态包判停与最后一个转动判停。
- 5/10/20/30 TPS 连续和突发输入，最后逻辑状态、计步、原始时间戳一致；“丢动画”不能变成“丢数据”。
- 六底色 CFOP、XCross、多 F2L 同时完成、OLL/PLL skip、AUF、重复半转、状态修正和停表后补充日志；复盘逐步状态和最终状态正确。
- 详情编辑期间分析回包、删除期间分析回包、同会话多次快速训练，不发生旧结果覆盖或旧回放 timer 污染。
- 统计 DNF/+2/并列、排序筛选、全选/跨窗口选择、跳到 PB、导入导出和撤销；虚拟列表不改变数据范围。
- 页面 reduced-motion、键盘操作、文字可读性、焦点进出/resize；GPU 资源和事件监听随生命周期释放。

保留 359 项既有测试并补行为级回归。部分测试直接匹配源码结构，实施重构时需要改为验证相同行为，不能通过删测试或维持坏结构“保绿”。

## 6. 复跑与后续证据

```sh
mkdir -p output/performance-audit
node scripts/performance-audit.mjs > output/performance-audit/node-baseline.json
npm test
```

CPU 脚本只创建合成数据，但会启动项目已有 Java 求解/打乱进程；未安装 Java 时结果会明确记录错误或 fallback 来源。不要把 fallback 样本与本轮 TNoodle 数字比较。
